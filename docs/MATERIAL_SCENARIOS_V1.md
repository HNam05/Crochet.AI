# Material gauge endpoint scenarios V1

`CARTESIAN_GAUGE_ENDPOINTS_V1` currently admits exactly one resolved `SINGLE_CROCHET` / `CYCLIC` response and creates a deterministic nominal case plus its four low/high stitch/course pitch corners. The endpoint is `nominal ± coverage_multiplier × standard_uncertainty`. Every endpoint must be finite and strictly positive. Scenario IDs, response ID, source MaterialProfile hash, scenario-policy hash, endpoint values, and scenario hash are retained. Multi-response uncertainty is unsupported; this five-case set must not be generalized into a full multi-response Cartesian claim.

The source MaterialProfile passes the existing schema and semantic validator before scenario creation. This prevents changed observation records from being used to sidestep the profile's redundant gauge assertions. Both the public `validate_gauge_scenario` and `apply_gauge_scenario` require the admitted profile and policy, independently rebuild the five expected cases, and require exact membership. A self-consistent hash on forged endpoint data therefore does not authorize a scenario. Applying a scenario returns a frozen wrapper containing a replaced `ForwardGraph`; the base material hash remains unchanged and the scenario hash is separate. Stored observations, MaterialProfile, CrochetIR, and caller-owned graph are not modified.

The policy requires a finite positive coverage multiplier and explicit owner, rationale, unit, and validation path. The multiplier does not turn standard uncertainty into a bounded distribution. This finite empirical endpoint set does not establish continuous coverage, covariance, a normal confidence interval, independence, or population generality.

`evaluate_gauge_scenarios` rebuilds the five cases from the admitted MaterialProfile and policy, then compares them to the supplied tuple, checks all hashes and ordering, and only then invokes the server-owned callback under a cumulative run budget of at most nine. Each callback result must include a status, metric mapping, and failure list; a claimed PASS must include a nonempty finite metric vector and no failures. A failed endpoint remains a failure even if nominal passes. It retains every result and failure record and includes the worst-status result with its complete metrics. The aggregate explicitly sets `outcome_scope=CALLER_CALLBACK_DIAGNOSTIC_ONLY`, `authenticity=NOT_ESTABLISHED`, and `verification_claim=NOT_VERIFIED`. Incomplete sets or budgets stop before any callback; unexpected callback exceptions propagate. This caller-callback aggregation does not authenticate robustness or establish V8; an internal numerical factory must independently compute its gate evidence.

The callback must independently run the admitted forward/geometry predicates for that scenario. It must not accept target geometry as a forward-model input or replace V6/V7 evidence with this scenario summary.
